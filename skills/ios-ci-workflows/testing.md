# 测试维护：写对位置，防止膨胀

目标：测试长期又快又稳，但不为了快而砍覆盖。效率靠“放对层、写对方式”换，不靠删测试。

这页只定原则。具体测什么、关键流程有几条，由你读完这个 App 的代码后判断，写进 App 仓库的 `TESTING.md`，开发者确认后才算数。

## 分层：放在能验证它的最便宜的一层

| 层 | 适合验证 | 代价 |
| --- | --- | --- |
| 逻辑测试（含迁移测试） | 计算、规则、数据读写、格式转换、状态变化 | 毫秒级，快线每次跑 |
| 快照测试 | 某个组件或页面在给定数据和外观下长什么样 | 秒级，快线每次跑 |
| UI 流程测试 | 多个页面串起来，用户真的能走通；顺带做无障碍审计 | 每条几十秒，只在慢线跑 |

一项检查能在下层验证，就不要放到上层：

- 规则算得对不对，写逻辑测试，不要在 UI 测试里点进页面去读数字。
- 页面显示对不对，写快照测试，不要在 UI 测试里逐个断言文字。
- 只有“这几步连起来能不能走通”才需要 UI 流程测试。

## 底线：每个 App 至少要覆盖的类别

这里只列类别。具体有哪些、各写几条，按 App 盘点后写进 `TESTING.md`。

1. **核心计算逻辑的边界情况**：App 最核心的那几条规则，边界值、空输入、跨越边界（跨天、跨月、跨年、闰年、时区等，按 App 实际情况）。
2. **会持久化的用户数据，含迁移**：存下去再读回来不变；旧版本写的数据新版本能读；缺字段、多字段、字段改名时有合理的默认值。每发一个正式版，把那个版本写出的样例数据存进测试目录，用新代码读它。
3. **依赖当前时间的逻辑**：把“现在”作为参数传进去，不在逻辑里直接调用 `Date()`；测试时传固定时间。直接读当前时间的代码只留在最外层（界面、定时器）。
4. **关键流程**：用户最常走、坏了影响最大的几条路径。哪些算关键、有几条，由你按 App 判断，开发者确认，不规定条数。
5. **主要页面及高风险状态**：每个主要页面至少一张快照；再加上容易出问题的状态，如空数据、超长文字、数据很多、深色模式、大字号。
6. **修过的 bug**：每修一个 bug，加一条能复现它的最小测试，放在能复现它的最便宜的一层；测试名或注释里写明是哪个问题。

## 写法

- **测行为，不测实现。** 断言用户能观察到的结果（算出的值、存下的数据、显示的内容），不断言内部调用了哪个函数、调了几次。重构不改行为时，测试不应该跟着改。
- **先改后加。** 要加测试时，先看 `TESTING.md` 和已有测试：已有测试覆盖同一个行为的，改它或给它加参数，不另起一个。
- **一个行为只测一次。** 同一类情况用参数化合并（Swift Testing 的 `@Test(arguments:)`，或 XCTest 里循环一组输入），不要复制出几个只差输入的测试。
- **不用固定等待。** UI 测试里不写 `sleep`、不固定等几秒；用 `waitForExistence` 或按条件轮询，等到条件满足就继续。
- **无障碍审计放在关键流程里顺带做**：流程走到哪一页，就在那一页调用 `performAccessibilityAudit()`，不为审计单独启动 App（写法见 [daily.md](daily.md)）。
- **测试数据固定。** 日期、示例数据、随机数都固定下来，同一份代码每次跑结果一样。

## 删除规则

只有三种情况能删测试：

| 情况 | PR 里要写明 |
| --- | --- |
| 它测的功能已经删除 | 删的是哪个功能 |
| 和另一个测试完全重复 | 和哪个测试重复 |
| 已被更低层的测试覆盖 | 被哪个测试覆盖 |

“太慢”不是删除理由：慢的测试先优化（去掉固定等待、少启动一次 App、换更小的数据）；还慢就挪到慢线，或把它验证的内容下沉到更便宜的层，再按上表第三种情况删掉原来的。

删测试、改断言预期值都要在 PR 里写明理由（见 [SKILL.md](SKILL.md)）。

## `TESTING.md`：每个 App 的测试清单

放在 App 仓库根目录，写这个 App：

- 按层列出测了什么、为什么测（对应上面哪一类底线）；
- 关键流程和主要页面各是哪些；
- 目前没覆盖到的地方，以及打算放在哪一层补。

增删测试时同步更新它，它就是“先改后加”时查的那份清单。

### 首次接入

1. 先读代码：数据模型、存储、核心规则、页面结构、哪里用到当前时间。
2. 按上面六类底线盘点：每一类在这个 App 里具体是什么、已有哪些测试、缺什么。
3. 写 `TESTING.md` 初稿，把关键流程、主要页面和缺口列出来。
4. 交开发者确认关键流程和主要页面的判断；确认之后再按缺口补测试。

## 发版前体检

发正式版前做一次，简单的 App 可以快速过一遍或跳过。

1. **统计一次**：手动跑一次 Build & Test 的 `full`，读测试结果：
   - 各层测试数量：报告开头的总数，以及 `report.json` 里的 `counts`；按 target 分层时看 `xcodebuild.log` 里的 `Test Suite` 行。
   - 总耗时：测试 job 的用时和 “Build and run tests” 这一步的用时。
   - 最慢的几个测试：`xcodebuild.log` 里每条 `Test Case ... passed (N seconds)`，按秒数排序取前几个。
2. **和上一个发版版本对比**：找上一个发版标签那个提交上的 Build & Test 运行（`full`，或 main 上的慢线加 PR 上的快线），用同样的方法读出三项，看哪一层涨得快、哪些测试变慢了。
3. **整理**，按顺序：
   - 合并重复：同一行为的多个测试合成一个参数化测试。
   - 删除过时：只按上面的删除规则。
   - 下沉：能在更便宜的层验证的，挪下去。
   - 优化最慢的：去掉固定等待，合并能在一次启动里走完的流程。
4. **产出一个 PR**：逐条写改了什么、为什么；每一处删除都对应删除规则里的一种情况和对应的测试；同时更新 `TESTING.md`。

## 不做的

不写统计脚本、不做每次运行的趋势对比、不查覆盖率、不做失败自动重跑。需要时再临时加：怀疑整理时砍多了，再开一次覆盖率看看；UI 测试明显时好时坏，再考虑重跑。
