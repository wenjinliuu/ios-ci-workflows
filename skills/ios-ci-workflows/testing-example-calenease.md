# 示例：CalenEase 的测试盘点

> **仅作示例。** 这是把 [testing.md](testing.md) 的原则套到一个具体 App 上的样子，用来说明每一步产出什么。别的 App 的关键流程、主要页面和测试内容都要按它自己的代码判断，不要照搬这里的条目和数量。

CalenEase（省心日历）是一个循环班表 App：排班按循环生成，另有日程、倒数日、工时统计、节假日和农历、备份。完整的清单在它仓库根目录的 [`TESTING.md`](https://github.com/wenjinliuu/calenease/blob/main/TESTING.md)。

## 1. 读代码时关注什么

| 看什么 | 在 CalenEase 里是 |
| --- | --- |
| 数据模型和存储 | 一个 JSON 文档（班次、记录、日程、倒数日、设置），本机加 iCloud 备份 |
| 核心规则 | 循环排班、工时和加班、节假日和调休、农历、重复日程、倒数日、提醒计划 |
| 哪里读当前时间 | 规则层都接收 `today:` / `now:` 参数；只有存储层、界面和导出文件名直接读 `Date()` |
| 页面结构 | 四个标签页（日历、事项、工时、设置），加若干弹窗 |

## 2. 按底线类别盘点

| 底线类别 | 在 CalenEase 里指什么 | 已有 | 缺口 |
| --- | --- | --- | --- |
| 核心计算的边界 | 循环跨年、跨午夜班次、2 月 29 日、没有 31 号的月份、四种工时制、未发布放假安排的年份 | 逻辑测试，分在五个文件 | 农历闰月的显示；循环跨 2 月 29 日 |
| 持久化与迁移 | 旧版数据迁到固定班次 ID、缺字段的老文件、备份往返、旧备份名 | 逻辑测试，散在四个文件 | 还没有“正式版真实写出的数据文件” |
| 依赖当前时间 | 提醒计划、倒数日、已记录天数、加班只算已过去的天 | 都传固定日期测 | 无 |
| 关键流程 | 首次引导、生成排班、改某天班次、切月回到今天、新建日程、备份恢复 | UI 测试 4 条 | 首次引导、生成排班、备份恢复 |
| 主要页面和高风险状态 | 日历、当天编辑、事项、新建日程、工时、设置；空数据、超长标题、大字号 | 日历组件快照 4 张 | 其余页面没有快照，高风险状态基本没有 |
| 修过的 bug | — | 看不出哪些是回归测试 | 今后在测试名或注释里写明是哪个问题 |

## 3. 按层归位的例子

| 要验证的事 | 放哪一层 | 为什么 |
| --- | --- | --- |
| 综合工时制下，月底少上的小时让加班变成负数 | 逻辑 | 纯计算，毫秒级就能验证 |
| 事项页一条超长标题会不会把布局挤乱 | 快照 | 看的是长什么样，不需要点 |
| 从月历点今天、改成请假、格子跟着变 | UI 流程 | 要验证的是几步连起来能走通 |
| 事项页的点击区域够不够大 | UI 流程里顺带审计 | 流程已经走到这一页，不为它单独启动 App |
| 从备份文件恢复出完整数据 | 逻辑（先），UI（只走本机备份） | 恢复逻辑在逻辑层就能验证；模拟器上 iCloud 不可靠 |

## 4. 交给开发者确认的内容

`TESTING.md` 初稿里列出了关键流程和主要页面，并标出哪些“待确认”。开发者确认后，才按缺口补测试；补的时候先查清单，已有测试覆盖同一行为的就改它或加参数。

## 5. 发版前体检会看的地方

- 两个节日测试文件是否在测同一件事，能否合并。
- 分散在四个文件里的迁移测试是否集中，方便对照各版本的数据格式。
- 最慢的两条 UI 流程（每条约 80～90 秒，主要花在无障碍审计上）能否再省。
- 月历左右滑动后固定等了 0.6 秒，应改成等到月份标题变化为止。
